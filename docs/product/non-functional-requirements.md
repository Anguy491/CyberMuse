## 测量基线

除非单项另有说明，Windows 实机基线为 Windows 11 x64、4 个现代 CPU 核心、16 GB RAM、集成声卡、无独立 GPU、48 kHz 输入，耳机避免扬声器串音。性能报告必须记录 CPU、RAM、设备、采样率、构建类型和样本数量。

## 平台与兼容

### NFR-001 — 支持平台

v0.1 必须在仍受 Microsoft 支持的 Windows 11 x64 版本上安装、启动、卸载，并使用系统 WebView2。其他平台不作为发布阻塞项。验证：干净虚拟机安装测试与一台真实音频设备机器的端到端测试。

### NFR-002 — 文件系统兼容

所有输入、缓存和导出路径必须支持 Unicode、空格、长文件名和 Windows 路径分隔符；不得依赖当前工作目录。验证：含中文、空格和至少 180 字符完整路径的契约与端到端测试。

## 实时性能

### NFR-003 — 视觉反馈延迟

从音频样本到达 AudioWorklet 到对应稳定音高观察可供 UI 绘制的软件路径延迟，P95 不得超过 100 ms，P99 不得超过 150 ms；物理设备输入延迟单独校准。验证：带单调时钟的发布构建至少采集 1,000 个有效观察。

### NFR-004 — 播放同步与漂移

参考轨、用户轨和播放 NOW 都必须从同一 `AudioContext` 时基派生。连续播放 10 分钟后，参考位置与播放位置绝对漂移不超过 20 ms；A-B 循环边界误差 P95 不超过 30 ms。验证：自动时钟测试加 Windows 实机回环测试。

### NFR-005 — UI 更新与稳定性

Worker 可按约 21 ms hop 产生观察，但 UI 绘制频率限制在 30–60 FPS。连续稳定音中，阈值边缘不得在 500 ms 内出现超过两次反馈等级往返。验证：受控时钟和阈值夹具测试。

### NFR-006 — 音频线程安全

AudioWorklet 回调不得执行网络、文件、模型、React、Tauri IPC 或不可预测分配。发布构建 30 分钟练习不得发生由应用处理造成的音频 underrun。验证：代码审查、性能记录和实机 soak test。

## 资源与分析器

### NFR-007 — CPU 基线

实时麦克风检测和绘制必须在测量基线设备上 CPU-only 运行，练习期间应用 CPU 的 60 秒 P95 不超过单机总 CPU 的 25%，工作集 P95 不超过 750 MB。验证：发布构建性能采样；超标阻止 M6。

### NFR-008 — 分析器可用性

离线 analyzer 必须可在 CPU-only 环境完成受支持歌曲分析，GPU 仅为可选加速。M4 性能 spike 必须记录 3、5、10 分钟歌曲的实时倍数、峰值 RAM 和磁盘临时空间，再由 ADR 确认发布预算；在该测量完成前，FR-004 的进度、取消和 UI 不阻塞是硬性门禁。

### NFR-009 — 取消响应

用户取消分析后，桌面端应在 500 ms 内显示 `cancelling`，analyzer 应在 5 秒内退出或被受控终止；最后有效缓存保持可用。验证：各 pipeline 阶段的契约测试和实机进程测试。

## 可靠性与数据完整性

### NFR-010 — 原子持久化

manifest、歌曲元数据、设置和 session 使用临时文件、flush、原子替换；崩溃不得把上一个有效版本变成半写文件。验证：在写入阶段注入进程终止并重启检查。

### NFR-011 — 可恢复错误

权限拒绝、设备消失、sidecar 崩溃、模型缺失、离线、磁盘不足、资产缺失必须成为结构化、可操作错误；不得导致 Library 数据丢失或应用启动失败。验证：每类至少一个自动或人工故障注入场景。

### NFR-012 — 长时间稳定性

发布候选必须通过 30 分钟连续练习和 25 次 A-B loop soak test：无崩溃、无持续增长超过 150 MB 的工作集、无失控音频节点累积。验证：M6 Windows 实机证据。

## 隐私、安全与网络

### NFR-013 — 本地优先

歌曲、派生音频、麦克风观察、练习记录和诊断默认仅存本机。应用不得包含默认启用的遥测或上传路径。验证：静态网络调用审查与受控网络捕获。

### NFR-014 — 有限联网

v0.1 只允许用户触发的模型下载和显式更新检查；首次联网前说明目的、目标域、大小和许可证。所有核心练习在模型已安装后离线可用。验证：断网端到端测试和网络 allowlist 测试。

### NFR-015 — 敏感日志最小化

日志不得包含音频字节、F0 全轨、完整原始文件名或路径、用户账户标识。路径使用不可逆短哈希或仅保留扩展名；默认日志保留 14 天且可清除。验证：诊断包自动扫描和人工审查。

### NFR-016 — 供应链完整性

生产包、模型和下载资产必须固定版本与 SHA-256；依赖及权重许可证在采用前通过策略审查。验证：锁文件、模型清单、SBOM/第三方声明和离线安装测试。

## 可访问性与可用性

### NFR-017 — 不只依赖颜色

音高状态、错误和分析进度必须同时用文字、位置、图标或形状表达。Dark/light 均为一等主题并以 WCAG 2.2 AA 为目标：正文对比度至少 4.5:1，重要非文本图形、控件边界和焦点至少 3:1。主要操作可使用键盘完成，焦点可见且不被遮挡；拖拽操作有等价按钮或键盘路径，并尊重 `prefers-reduced-motion` 与 Windows forced-colors。自托管字体加载失败或断网时必须回退到本地系统字体且不阻塞主流程。验证：两套 token 对比度、键盘 walkthrough、dark/light 灰度/forced-colors 截图、reduced-motion、断网字体 fallback 和自动可访问性检查。

### NFR-018 — 错误可操作

用户可见错误必须包含发生事项、数据状态、下一步动作和稳定错误码，不向用户展示 Python traceback 或 Rust panic。验证：UX 状态测试与错误目录审查。

## 可维护性与发布

### NFR-019 — 契约版本

所有持久化 JSON、CLI 与 IPC payload 必须有明确版本；读端拒绝未知主版本，并对同主版本新增可选字段保持向前兼容。验证：契约 fixture 覆盖旧版、当前版、未知主版本和额外字段。

### NFR-020 — 质量门禁

发布候选必须通过类型检查、lint、单元、契约、集成、端到端、性能、许可证和安装验证。Must 需求不得依赖跳过测试；代码覆盖率仅作趋势指标，核心 scoring、schema 和错误映射分支覆盖率不得低于 90%。

### NFR-021 — 可复现构建

相同提交、锁文件、工具链版本和模型清单应生成内容等价的应用行为；构建手册不得依赖未记录的全局包。验证：干净 Windows 环境按 runbook 完成构建。
